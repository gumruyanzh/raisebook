## 1. Product

### 1.1 One-liner
Raisebook keeps your raise in one ledger: every investor, in every round, with stage, fit,
follow-up, notes and commitment. It is free forever and open source, and your own agent (Claude
Code, Codex, Cursor, any MCP client) can work the pipeline with you, with every agent action
shown on the timeline.

### 1.2 Why it exists
Founders run raises from spreadsheets because the CRMs built for fundraising are paid, and
they are often built to collect founders' data into an investor database. Raisebook is the
opposite: free, private per workspace, exportable, deletable, and open source, so anyone can
check the promise in the code.

### 1.3 Personas
1. **Solo founder raising a pre-seed or seed** (primary). Has 50 to 400 investor names in a
   spreadsheet, notes in their head, and follow-ups slipping. Uses Claude Code or Codex daily.
   Wants a board, a list of due follow-ups, and an agent that can "log that call and remind me
   Friday."
2. **Co-founder pair.** One runs the raise and the other takes some meetings. They need shared
   state, an owner per investor, and a view-only role for an advisor.
3. **Founder's agent** (first-class user). An MCP client with a scoped key. It researches,
   imports, logs and sets follow-ups. Everything it does must be idempotent where possible,
   attributed, and easy for the human to review.
4. **Self-hoster / contributor.** Runs `docker compose up` on their own box and reads the code.

### 1.4 MVP scope (this build)
- Magic-link sign-in; workspaces (one per company); members with owner/editor/viewer roles;
  email invites.
- Rounds with terms (target, instrument, cap or pre-money, target close date, open/closed) and
  ordered, customizable stages with colors. Default stages are in §3.3.
- Investor contacts at workspace level, reusable across rounds, with dedupe on email, LinkedIn
  and name+firm.
- Round participation per investor: stage, fit 0..5, follow-up date and note, soft and
  committed amounts, probability, owner, next step.
- Activity timeline (append-only), with the actor (user, agent with name and model, or
  system).
- Round pipeline page: ledger strip (committed vs target, funnel, due follow-ups), Board (drag
  and keyboard), Table (sort, filter), Investor sheet. Round overview page. Investors directory
  and investor page.
- Workspace API keys with scopes, a REST API under `/v1` with OpenAPI, and an MCP server at
  `/mcp` with the 17 tools in §6 (plus the 5 research tools of §6.7, unreleased and served
  only with `RAISEBOOK_RESEARCH_ENABLED`). Rate limits per key.
- CSV import (mapping, preview, dedupe), CSV and JSON export, prototype JSON import (should
  have, built after CSV).
- Sample (sandbox) workspace with fictional data.
- Hard delete of an investor, round, workspace or account. Full export at any time.
- Landing page, docs (MCP setup, REST reference, CSV format, self-hosting), privacy page.
- Dockerfiles, `deploy/docker-compose.yml`, `deploy/Caddyfile`. CI workflows.

### 1.5 Later (not in this build; do not stub UI for these)
- OAuth 2.1 for MCP so web-only connectors (claude.ai, ChatGPT) can connect without pasting a key.
- Daily or weekly email digest of due follow-ups (opt-in per member).
- Gmail / Outlook BCC address to log emails automatically; calendar sync for meetings.
- Re-import of a Raisebook JSON export (restore into an empty workspace).
- Investor merge UI (merge two contacts and their timelines).
- Postgres row-level security as defense in depth (MVP enforces isolation in the app layer
  with mandatory tests, §9.2).
- Investor update emails (monthly updates to investors), data room, cap table.
- GitHub Sponsors / Open Collective integration beyond a link.
- Per-round permissions, comments and mentions.

### 1.6 Non-goals (never)
- **No investor database built from user data.** No cross-workspace suggestions ("investors you
  might know"), enrichment from other workspaces, shared contact graph, or benchmarking across
  workspaces. No query in the codebase may read rows from more than one workspace, except
  admin counts of rows per table for capacity planning, and the operator's research
  **removal** action (`services/research_removal.py`, R13), which only *deletes* research rows
  about a person who asked, in every workspace, and returns counts, never content; and research
  **reuse across one owner's workspaces** (`services/research_reuse.py`, RESEARCH-SPEC #15),
  which reads only the public layer (identity, accepted sources, cited public facts) of another
  workspace when the person asking owns both, never private analysis or notes.
- No paid tier, ads, sponsored placements or selling data.
- No third-party trackers, analytics scripts, session replay or marketing pixels. Fonts are
  self-hosted (`next/font`), and the web app loads no third-party scripts at runtime.
- Raisebook never pays for or runs models on its own, and never sends workspace data to an
  LLM provider on its own initiative. Investor research (docs/RESEARCH-SPEC.md) is
  bring-your-own-key: it calls OpenRouter **only with the workspace's own key**, only when a
  member presses a button or an agent asks, and sends only what docs/RESEARCH-PLAN.md §11.4
  lists (the investor's identity fields, the company profile and round terms; never notes,
  emails, amounts or timelines). Agents connect with the user's key.
- No scraping LinkedIn or other sites: Raisebook's servers never fetch third-party pages
  (research search runs inside OpenRouter). No sending emails to investors on the user's behalf in
  MVP.
- Not a sales CRM, not a cap-table tool, not an investor-facing portal.

## 2. Architecture

```
raisebook.org (web, Next.js :3000) ──fetch /v1 (cookie + CSRF)──▶ api.raisebook.org (FastAPI :8000)
                                                                   ├─ /v1/*   REST (session cookie or API key)
MCP clients (Claude Code, Codex, Cursor) ──Bearer rb_live_…──────▶ ├─ /mcp    MCP streamable HTTP (API key)
                                                                   ├─ /healthz, /healthz/ready
                                                                   └─ Postgres 17
```

- One API process type. No worker in MVP: emails are sent inline (with a short timeout), and
  deletes are synchronous single transactions. Housekeeping (expired tokens, old rate-limit
  windows) runs through `rbctl housekeeping`, which ops can cron later.
- The web app calls the API from the browser (`credentials: "include"`) and from server
  components (forwarding the cookie). The session cookie is set for the parent domain in
  production (`RAISEBOOK_SESSION_COOKIE_DOMAIN=raisebook.org`) so both hosts see it. Locally,
  `localhost` cookies are shared across ports.
- Every workspace-scoped row carries `workspace_id`. Child tables use composite foreign keys
  `(workspace_id, parent_id)`, so the database itself cannot link rows across workspaces.

## 3. Data model (Postgres 17)

Conventions:
- Primary keys are `uuid DEFAULT gen_random_uuid()`. Timestamps are `timestamptz`; dates are
  `date`. `created_at`/`updated_at` default `now()`; services set `updated_at` from the
  injected clock.
- Enumerations are `text` + `CHECK` (no Postgres enum types), as in smmist.
- Extensions: `citext`, `pg_trgm` (created in `public`; the test harness creates them if missing).
- Constraint names follow the SQLAlchemy naming convention (`pk_`, `fk_`, `uq_`, `ck_`, `ix_`).
- All tables ship in `alembic/versions/0001_init.py`. Feature builders do not add migrations
  (`docs/OWNERSHIP.md`).
- Lengths and array limits in `CHECK`s are the hard limit. Services validate the same limits
  first and return `validation_error` with the field name.

### 3.1 Identity and access

```sql
CREATE TABLE users (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email          citext NOT NULL UNIQUE CHECK (length(email) <= 254 AND position('@' IN email) > 1),
  name           text CHECK (name IS NULL OR length(btrim(name)) BETWEEN 1 AND 120),
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  last_signin_at timestamptz,
  -- Continue with Google (migration 0002): the Google account id (OIDC `sub`), bound on the
  -- first Google sign-in. Null for magic-link-only accounts; one Google account, one user.
  google_sub     text UNIQUE CHECK (google_sub IS NULL OR length(google_sub) BETWEEN 1 AND 255)
);

-- Magic links. The user row is created on first successful verify, not on request.
CREATE TABLE login_tokens (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email         citext NOT NULL,
  token_hash    bytea NOT NULL UNIQUE,            -- sha256(token); token is 32 random bytes, base64url
  redirect_path text CHECK (redirect_path IS NULL OR (left(redirect_path, 1) = '/' AND left(redirect_path, 2) <> '//')),
  requested_ip  inet,
  created_at    timestamptz NOT NULL DEFAULT now(),
  expires_at    timestamptz NOT NULL,             -- created_at + 15 min
  consumed_at   timestamptz
);
CREATE INDEX ix_login_tokens_email_created ON login_tokens (email, created_at DESC);

CREATE TABLE user_sessions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL REFERENCES users ON DELETE CASCADE,
  secret_hash  bytea NOT NULL,                    -- sha256(cookie secret)
  created_at   timestamptz NOT NULL DEFAULT now(),
  expires_at   timestamptz NOT NULL,              -- sliding, 30 days
  last_seen_at timestamptz,
  revoked_at   timestamptz,
  user_agent   text CHECK (user_agent IS NULL OR length(user_agent) <= 400),
  ip           inet
);
CREATE INDEX ix_user_sessions_user ON user_sessions (user_id);

CREATE TABLE workspaces (
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug               citext NOT NULL UNIQUE CHECK (slug ~ '^[a-z0-9][a-z0-9-]{1,46}[a-z0-9]$'),
  name               text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 80),
  is_sandbox         boolean NOT NULL DEFAULT false,
  default_currency   char(3) NOT NULL DEFAULT 'USD' CHECK (default_currency ~ '^[A-Z]{3}$'),
  timezone           text NOT NULL DEFAULT 'UTC',  -- IANA name, validated with zoneinfo in the service
  created_by_user_id uuid REFERENCES users ON DELETE SET NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE memberships (
  workspace_id uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  user_id      uuid NOT NULL REFERENCES users ON DELETE CASCADE,
  role         text NOT NULL CHECK (role IN ('owner', 'editor', 'viewer')),
  created_at   timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (workspace_id, user_id)
);
CREATE INDEX ix_memberships_user ON memberships (user_id);

CREATE TABLE invites (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id        uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  email               citext NOT NULL CHECK (length(email) <= 254),
  role                text NOT NULL CHECK (role IN ('owner', 'editor', 'viewer')),
  token_hash          bytea NOT NULL UNIQUE,
  invited_by_user_id  uuid REFERENCES users ON DELETE SET NULL,
  created_at          timestamptz NOT NULL DEFAULT now(),
  expires_at          timestamptz NOT NULL,       -- created_at + 7 days
  accepted_at         timestamptz,
  accepted_by_user_id uuid REFERENCES users ON DELETE SET NULL,
  revoked_at          timestamptz
);
CREATE UNIQUE INDEX uq_invites_pending ON invites (workspace_id, email)
  WHERE accepted_at IS NULL AND revoked_at IS NULL;

CREATE TABLE api_keys (
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id       uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  name               text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 80),
  agent_name         text CHECK (agent_name IS NULL OR agent_name ~ '^[A-Za-z0-9][A-Za-z0-9 ._-]{0,59}$'),
  key_prefix         text NOT NULL,               -- first 12 chars, e.g. "rb_live_Ab3x"
  key_hash           bytea NOT NULL UNIQUE,       -- sha256(plaintext)
  mode               text NOT NULL CHECK (mode IN ('live', 'test')),
  scopes             text[] NOT NULL CHECK (
                       cardinality(scopes) >= 1
                       AND scopes <@ ARRAY['raisebook:read', 'raisebook:write', 'raisebook:admin']::text[]
                       AND 'raisebook:read' = ANY (scopes)),
  created_by_user_id uuid REFERENCES users ON DELETE SET NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),
  last_used_at       timestamptz,
  expires_at         timestamptz,
  revoked_at         timestamptz
);
CREATE INDEX ix_api_keys_workspace ON api_keys (workspace_id);
```

Rules enforced in services:
- Workspace slug: `slugify(name)[:43] + "-" + 4 random lowercase base32 chars` (for example
  `tallow-k7p2`), generated once and never changed. The random suffix means a slug never reveals
  that another workspace with the same name exists.
- `api_keys.mode` must match the workspace: `test` keys only for `is_sandbox` workspaces,
  `live` keys only for real ones. `raisebook:admin` requires `raisebook:write`.
- Limits per workspace: 20 members (including pending invites), 20 active API keys, 50 rounds,
  20,000 investors, 1,000,000 activities. Exceeding one returns 422 `limit_reached`.
- A workspace always has at least one owner. Removing or demoting the last owner returns 409
  `last_owner`.

### 3.2 Rounds and stages

```sql
CREATE TABLE rounds (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id        uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  slug                citext NOT NULL CHECK (slug ~ '^[a-z0-9][a-z0-9-]{0,47}$'),
  name                text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 80),
  status              text NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'closed')),
  instrument          text NOT NULL DEFAULT 'safe'
                        CHECK (instrument IN ('safe', 'priced', 'convertible_note', 'other')),
  currency            char(3) NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
  target_amount       bigint NOT NULL DEFAULT 0 CHECK (target_amount >= 0),
  valuation_cap       bigint CHECK (valuation_cap IS NULL OR valuation_cap > 0),
  pre_money_valuation bigint CHECK (pre_money_valuation IS NULL OR pre_money_valuation > 0),
  target_close_on     date,
  closed_on           date CHECK (closed_on IS NULL OR status = 'closed'),
  notes               text CHECK (notes IS NULL OR length(notes) <= 20000),
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now(),
  UNIQUE (workspace_id, id),
  UNIQUE (workspace_id, slug)
);
CREATE UNIQUE INDEX uq_rounds_ws_name ON rounds (workspace_id, lower(name));

CREATE TABLE round_stages (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id uuid NOT NULL,
  round_id     uuid NOT NULL,
  key          text NOT NULL CHECK (key ~ '^[a-z][a-z0-9_]{0,31}$'),
  label        text NOT NULL CHECK (length(btrim(label)) BETWEEN 1 AND 40),
  color        text NOT NULL CHECK (color IN ('slate', 'violet', 'cobalt', 'teal', 'amber',
                                              'orange', 'green', 'gray', 'olive', 'sky')),
  kind         text NOT NULL CHECK (kind IN ('open', 'active', 'won', 'lost')),
  position     smallint NOT NULL CHECK (position BETWEEN 0 AND 31),
  FOREIGN KEY (workspace_id, round_id) REFERENCES rounds (workspace_id, id) ON DELETE CASCADE,
  UNIQUE (round_id, id),
  UNIQUE (round_id, key),
  CONSTRAINT uq_round_stages_position UNIQUE (round_id, position) DEFERRABLE INITIALLY DEFERRED
);
CREATE UNIQUE INDEX uq_round_stages_one_won  ON round_stages (round_id) WHERE kind = 'won';
CREATE UNIQUE INDEX uq_round_stages_one_lost ON round_stages (round_id) WHERE kind = 'lost';
```

Slug: `slugify(name)`, with `-2`, `-3` and so on appended on collision within the workspace.
It may change when the round is renamed; ids are the stable reference. A round name is
unique per workspace (case-insensitive), so `POST /v1/rounds` with an existing name returns 409
`duplicate` with the existing round (agents can treat this as idempotent).

### 3.3 Stage semantics and defaults

Stage `kind` drives every computed number:
- `open`: on the list, not contacted yet. Not counted as "in conversation".
- `active`: in conversation.
- `won`: exactly one per round, the committed stage. Only participants in it count toward
  `committed`.
- `lost`: exactly one per round, passed or dead. Excluded from soft and weighted totals.

Default stages created with every round (keys match `prototype.html`):

| pos | key | label | color | kind |
|---|---|---|---|---|
| 0 | `new` | New | slate | open |
| 1 | `research` | Researching | violet | open |
| 2 | `contacted` | Contacted | cobalt | active |
| 3 | `replied` | Replied | teal | active |
| 4 | `meeting` | Meeting | amber | active |
| 5 | `dd` | Diligence | orange | active |
| 6 | `committed` | Committed | green | won |
| 7 | `passed` | Passed | gray | lost |

Stage editing (`PUT /v1/rounds/{round}/stages`, §5.6) replaces the whole ordered list in one
transaction:
- 3 to 16 stages; exactly one `won` and one `lost`; at least one `open` or `active`.
- Existing stages are matched by `key`. A new stage's key is `slugify(label, "_")`, made unique.
  Keys are immutable; labels, colors, kinds and order may change.
- A removed stage that still has participants needs `reassign: {"<removed_key>": "<target_key>"}`,
  or the call fails with 409 `stage_in_use` and the counts. Each reassigned participant gets a
  `stage_change` activity with `data.reason = "stage_removed"`.

### 3.4 Investors (workspace contacts)

```sql
CREATE TABLE investors (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id   uuid NOT NULL REFERENCES workspaces ON DELETE CASCADE,
  name           text NOT NULL CHECK (length(btrim(name)) BETWEEN 1 AND 200),
  firm           text CHECK (firm IS NULL OR length(firm) <= 200),
  title          text CHECK (title IS NULL OR length(title) <= 200),
  type           text NOT NULL DEFAULT 'other' CHECK (type IN ('vc', 'angel', 'family_office',
                   'corporate_vc', 'accelerator', 'scout', 'other')),
  check_min      bigint CHECK (check_min IS NULL OR check_min >= 0),
  check_max      bigint CHECK (check_max IS NULL OR check_max >= 0),
  check_note     text CHECK (check_note IS NULL OR length(check_note) <= 200),  -- "$250k-$1M, leads"
  stage_focus    text[] NOT NULL DEFAULT '{}',    -- suggested: pre-seed, seed, series-a, series-b, growth
  industries     text[] NOT NULL DEFAULT '{}',
  tags           text[] NOT NULL DEFAULT '{}',
  location       text CHECK (location IS NULL OR length(location) <= 200),
  email          citext CHECK (email IS NULL OR (length(email) <= 254 AND position('@' IN email) > 1)),
  linkedin_url   text CHECK (linkedin_url IS NULL OR length(linkedin_url) <= 500),
  website_url    text CHECK (website_url IS NULL OR length(website_url) <= 500),
  x_url          text CHECK (x_url IS NULL OR length(x_url) <= 500),
  notes          text CHECK (notes IS NULL OR length(notes) <= 20000),
  source         text CHECK (source IS NULL OR length(source) <= 200),         -- "SF Tech Week 2026"
  warm_intro_by  text CHECK (warm_intro_by IS NULL OR length(warm_intro_by) <= 200),
  -- maintained by services/normalize.py on every write; never set from input
  linkedin_key   text,                            -- "in/jane-doe-12ab" (lowercase path), NULL if not a profile URL
  name_key       text NOT NULL,                   -- norm(name) || '|' || norm(coalesce(firm, ''))
  search_text    text NOT NULL DEFAULT '',        -- lowercase: name firm title email location tags industries source notes[:2000]
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (workspace_id, id),
  CHECK (check_min IS NULL OR check_max IS NULL OR check_min <= check_max),
  CHECK (cardinality(stage_focus) <= 10 AND cardinality(industries) <= 30 AND cardinality(tags) <= 30)
);
CREATE UNIQUE INDEX uq_investors_ws_email    ON investors (workspace_id, email) WHERE email IS NOT NULL;
CREATE UNIQUE INDEX uq_investors_ws_linkedin ON investors (workspace_id, linkedin_key) WHERE linkedin_key IS NOT NULL;
CREATE INDEX ix_investors_ws_name_key ON investors (workspace_id, name_key);
CREATE INDEX ix_investors_ws_updated  ON investors (workspace_id, updated_at DESC);
CREATE INDEX ix_investors_search_trgm ON investors USING gin (search_text gin_trgm_ops);
CREATE INDEX ix_investors_tags        ON investors USING gin (tags);
CREATE INDEX ix_investors_industries  ON investors USING gin (industries);
```

Normalization (`services/normalize.py`, the single implementation that import, API and MCP
all use):
- Text fields: strip, collapse internal whitespace, empty string becomes NULL.
- Array items: strip, drop empties, 1 to 40 chars each, dedupe case-insensitively (keeping the
  first casing), preserve order.
- `norm(s)`: NFKD, strip accents, lowercase, `&` → `and`, drop punctuation, collapse spaces.
  Drop trailing firm suffixes (`capital`, `ventures`, `partners`, `vc`, `fund`, `llc`, `lp`,
  `inc`) only from the firm part of `name_key`.
- `linkedin_key`: accept `linkedin.com/in/<slug>` (any subdomain, with or without scheme,
  trailing slash or query) and return `in/<slug>` lowercased. `/search/`, `/company/` and other
  paths return NULL (the URL is kept, but not used for dedupe).
- URLs: if no scheme, prefix `https://`. Only `http`/`https` are allowed. `x_url` also accepts
  `@handle` and becomes `https://x.com/handle`.
- `check_note` is parsed for `check_min`/`check_max` when those are not given: `$250k`, `250K`,
  `1.5M`, `$250k-$1M`, `250,000 - 1,000,000`.

Dedupe match order (used by `add_investor`, `POST /v1/investors` and import):
1. same `email` (case-insensitive) → `matched_on: "email"`
2. same `linkedin_key` → `"linkedin"`
3. same `name_key` and both firms present (or both absent) → `"name_firm"`

`email` and `linkedin_key` matches are enforced by unique indexes. `name_firm` is advisory: a
`create_anyway` request skips it.

### 3.5 Round participation

```sql
CREATE TABLE round_participants (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
```

## 4. Authentication and authorization

### 4.1 Magic link
1. `POST /v1/auth/magic-link {email, redirect_path?, invite_token?}` always returns
   `202 {"sent": true}` (it never reveals whether an account exists). It stores a
   `login_tokens` row with a 15-minute expiry and emails the link
   `${RAISEBOOK_APP_URL}/auth/verify?token=<token>`. In dev, when the API's public URL is a
   localhost host (smmist's `echo_magic_links` rule), the response also contains
   `"dev_link"` and the link is logged.
2. The web page `/auth/verify` never spends the token on load. It shows "Sign in as
   j***@example.com" (from `GET /v1/auth/verify/peek?token=`, which only reports `{valid,
   email_hint}`) and POSTs `POST /v1/auth/verify {token, switch_account?}` when the person
   presses Continue, so link scanners (including ones that run JavaScript) cannot burn it.
   If the request already carries a valid session for a *different* user, verify returns 409
   `session_conflict` (details `signed_in_as`, `link_for`, masked) and spends nothing, unless
   `switch_account: true`, which revokes the old session. A forwarded link can therefore never
   silently swap someone into another account. (Polish pass.)
3. Verify: the token must exist, be unexpired and unconsumed. It is consumed atomically
   (`UPDATE … WHERE consumed_at IS NULL RETURNING`). The service upserts the user by email,
   sets `last_signin_at`, creates a `user_sessions` row, sets the cookies and returns
   `{user, csrf_token, redirect_path, workspaces}`. If an `invite_token` was attached and
   the emails match, it accepts the invite in the same transaction.
4. Rate limits: 5 requests per email per 15 minutes, 30 per IP per hour. Over the limit, the
   response is still 202 but no email is sent, and a warning is logged with the email hashed.

### 4.1a Continue with Google (UX pass 1, WS-G)
Off unless `RAISEBOOK_GOOGLE_CLIENT_ID` and `RAISEBOOK_GOOGLE_CLIENT_SECRET` are set.
`GET /v1/auth/providers` returns `{magic_link: true, google: bool}`; the web hides the button
when `google` is false (or the API cannot be asked within 3s).
1. `GET /v1/auth/google/start?next=` (a full-page navigation, not XHR) stores a signed state
   and PKCE verifier in a short-lived cookie and redirects to Google (OIDC). `next` must be a same-app relative path.
2. `GET /v1/auth/google/callback` checks the state, exchanges the code and verifies the ID
   token. A **verified** Google email signs into the existing account for that address (the
   same account as the emailed link) or creates one; `users.google_sub` is bound on first use.
   An unverified email is refused, and so is a different Google account claiming an address
   already bound to another `google_sub`. Finishing replaces any other session in that
   browser. Rate limits: per IP, and `RAISEBOOK_GOOGLE_MAX_PER_WINDOW` (10) sign-ins per
   account per `MAGIC_LINK_TTL_MINUTES`, counting emailed-link sign-ins too.
3. It lands on `/onboarding` when the user has no workspace, else on `next` or `/app`. If
   `next` is an invite (`/invite/<token>`), a new user lands there to accept it. A refusal
   lands on `/signin?error=<code>` (`google_not_configured`, `google_denied`,
   `google_failed`, `google_state_invalid`, `google_token_invalid`, `google_exchange_failed`,
   `google_unavailable`, `google_email_missing`, `google_email_unverified`,
   `google_account_mismatch`, `google_signin_refused`), and the page explains it. The flow is
   the OIDC authorization code flow with PKCE, `state` and `nonce` in a short-lived signed
   HttpOnly cookie.
The redirect URI to register with Google is exactly
`https://api.raisebook.org/v1/auth/google/callback` (`${PUBLIC_BASE_URL}/v1/auth/google/callback`).

### 4.2 Session cookie and CSRF (copy smmist `auth/session.py`, renamed)
- `rb_session` = `<session_id hex>.<secret>.<HMAC-SHA256(session_key, id.secret)>`. Flags:
  HttpOnly, Secure (`RAISEBOOK_SESSION_COOKIE_SECURE`, false only in dev), SameSite=Lax,
  Path=/, Domain=`RAISEBOOK_SESSION_COOKIE_DOMAIN` (unset locally), 30-day sliding expiry
  (touched at most every 5 min), and an absolute lifetime of 90 days from sign-in
  (`RAISEBOOK_SESSION_MAX_DAYS`). `GET /v1/me/sessions`, `DELETE /v1/me/sessions/{id}` and
  `POST /v1/me/sessions/revoke-others` let a person see and end their sessions. Every subdomain
  of the cookie domain receives the session cookie, so all of them must be first-party.
- `rb_csrf` (readable cookie) and `GET /v1/auth/session` both carry the CSRF token
  `HMAC(session_key, "csrf:" + session_id)`. Every cookie-authenticated unsafe method must send
  `X-CSRF-Token` and, when `Origin` is present, an allowed origin (`RAISEBOOK_APP_URL`,
  `RAISEBOOK_PUBLIC_BASE_URL`, `RAISEBOOK_CORS_ORIGINS`). A request that carries an API key is
  never cookie-authenticated.
- `RAISEBOOK_SESSION_SECRET` is required in staging and production (startup fails without
  it).

### 4.3 Workspace selection
- API key: the key's workspace. The `X-Workspace` header is ignored for keys.
- Session: header `X-Workspace: <workspace id or slug>`, checked against the user's
  memberships. A slug or id that is not one of the user's workspaces returns 404
  `workspace_not_found`. If the header is absent and the user has exactly one workspace, that
  workspace is used. Otherwise the response is 400 `workspace_required`. The web app always
  sends the header (the workspace slug is in the URL).
- Org-less session endpoints (`/v1/auth/*`, `/v1/me`, `GET/POST /v1/workspaces`,
  `/v1/invites/lookup`, `/v1/invites/accept`) do not need the header.

### 4.4 API keys (copy smmist `auth/api_keys.py`, renamed)
- Format `rb_live_` or `rb_test_` + 32 base62 characters. Only sha256 is stored. The
  plaintext is returned once, at creation. `key_prefix` is the first 12 characters.
- Accepted as `Authorization: Bearer <key>` or `X-API-Key: <key>` on `/v1/*` and `/mcp`.
- Revoked, expired or malformed keys return 401 `invalid_api_key` with
  `WWW-Authenticate: Bearer realm="raisebook"`. `last_used_at` is touched at most once per 60s.
- Keys are created and revoked only by an owner through a session (never by an API key, so an
  agent cannot mint or widen its own access).
- A key ends with its creator's access: removing a member (or a member leaving), demoting an
  owner, and deleting an account revoke every active key that person created, in the same
  transaction. `Member.active_api_keys` lets the UI warn before it happens. (Polish pass.)
- Requests presenting a key that fails to authenticate count against a per-IP `auth_fail`
  bucket (60/min, then 429), on `/v1` and `/mcp`. On `/mcp` a rejected key gets "Invalid or
  revoked Raisebook API key…" and a missing key setup guidance, not a generic 401.

### 4.7 Actor attribution (agents are first-class)
Every write produces activities stamped with:
- Session: `actor_type=user`, `actor_user_id`, `via=web`.
- API key on `/v1`: `actor_type=agent`, `api_key_id`, `via=api`.
- `/mcp`: `actor_type=agent`, `api_key_id`, `via=mcp`.
- Imports: same actor as above, `via=import`, `import_run_id`.
- Sample data and maintenance: `actor_type=system`, `actor_label="raisebook"`, `via=system`.

Agent name (`actor_label`): the `X-Agent-Name` request header (≤60 chars, same pattern as
`api_keys.agent_name`; invalid values are ignored), else `api_keys.agent_name`, else
`api_keys.name`. Agent model (`agent_model`): the `X-Agent-Model` header (≤80 printable
chars), else NULL. The MCP setup snippets (§6.5) set `X-Agent-Name`; `X-Agent-Model` is
offered as an optional extra header (it is static in a client config, so the snippets say to
update it when the model changes). MCP `clientInfo` is not available per call on the
stateless transport, so there is no automatic fallback. `core/actor.py` defines
`Actor(type, user_id, api_key_id, label, model, via)`, and every service write takes an
`actor: Actor`.

## 5. REST API `/v1`

### 5.1 Conventions
- JSON in and out (`application/json`). CSV export responses are `text/csv; charset=utf-8`
  with `Content-Disposition: attachment`.
- Ids are UUID strings. `{round}` in paths accepts a round id or slug. `{investor_id}` is a
  UUID.
- Timestamps are RFC 3339 UTC (`2026-10-10T17:04:05Z`). Dates are `YYYY-MM-DD`. Amounts are
  integers in whole units of the round's currency (or the workspace default currency for
  investor check sizes).
- PATCH semantics: absent key = unchanged; `null` = clear (not allowed for required fields).
- Lists: `?limit=` (default 50, max 200) and `?cursor=` (opaque). The response is
  `{"data": [...], "next_cursor": "…" | null}`.
- OpenAPI at `GET /v1/openapi.json`. FastAPI's Swagger UI at `/docs` is enabled only in dev
  (it loads assets from a CDN). The public REST reference is a web docs page.
- Every response carries `X-Request-ID`. Rate-limited routes carry `RateLimit-Limit`,
  `RateLimit-Remaining`, `RateLimit-Reset` (§7).
- Request body limit: 1 MB, except `/v1/imports*` (6 MB). Over the limit → 413
  `payload_too_large`.

### 5.2 Error envelope
```json
{"error": {"code": "not_in_round", "message": "Dana Whitfield is not in round Seed. Add them with POST /v1/rounds/seed/participants.", "details": {"investor_id": "…", "round": "seed"}, "request_id": "req_01J…"}}
```

| HTTP | code | When |
|---|---|---|
| 400 | `bad_request`, `workspace_required` | malformed request; session without `X-Workspace` and more than one workspace |
| 401 | `unauthorized`, `invalid_api_key`, `session_invalid` | no or bad credentials |
| 403 | `csrf_failed`, `insufficient_scope`, `forbidden_role` | §4 |
| 404 | `not_found`, `workspace_not_found` | missing or other-workspace resource |
| 409 | `duplicate` | unique conflict; `details.existing` holds the existing object (investor, round) |
| 409 | `ambiguous_reference` | an investor or round reference matches more than one; `details.candidates` lists up to 10 `{id, name, firm}` |
| 409 | `stage_in_use`, `last_owner`, `not_in_round`, `already_member`, `invite_mismatch`, `transfer_ownership_first` | state conflicts |
| 413 | `payload_too_large` | body or inline export too large |
| 422 | `validation_error` | Pydantic or service validation; `details: [{"loc": ["body","fit"], "msg": "…", "type": "…"}]` |
| 422 | `round_required`, `stage_not_found`, `invalid_stage_config`, `limit_reached`, `confirmation_required`, `import_invalid` | semantic errors |
| 429 | `rate_limited` | `Retry-After` header, `details.retry_after_s` |
| 500 | `internal_error` | message "Unexpected error. Reference <request_id>." (no stack, no SQL) |

Messages are full sentences an agent can act on, and say what to do next.

```ts
                     priority: "hot"|"warm"|"maybe"|"low"; probability?: number; amount_soft?: number;
                     amount_committed?: number; committed_on?: string; follow_up_on?: string; follow_up_note?: string;
                     follow_up_state?: "overdue"|"today"|"soon"|"later"; next_step?: string;
                     owner?: { user_id; name?; email }; stage_changed_at; last_activity_at?; created_at; updated_at };

                  data: object; actor: Actor; created_at; deletable: boolean };

                      follow_up_state: "overdue"|"today"|"soon"|"later"; days_overdue: number; follow_up_note?;
                      next_step?; last_activity_at? };

  money: { currency; target: number; committed: number; pct_of_target: number; soft_circled: number;

```

Summary math: `committed` = sum of `amount_committed` over participants in the `won` stage.
`soft_circled` = sum of `amount_soft` over `open` and `active` participants.
`weighted_pipeline` = sum of `amount_soft × coalesce(probability, 0) / 100` over `active`
participants. `pct_of_target` = committed / target × 100, rounded to 1 decimal (0 when the
target is 0).

## 6. MCP server

### 6.1 Transport and auth
- `POST|GET|DELETE /mcp`, an exact-path raw ASGI route (no Mount, so there is no 307
  redirect). Stateless streamable HTTP with JSON responses. The server name is `raisebook`.
  Copy smmist `mcp/server.py` and `mcp/auth.py`, including the lifespan note: the app
  lifespan must enter `server.session_manager.run()`.
- Auth: any valid Raisebook API key (`Authorization: Bearer` or `X-API-Key`). There is no
  separate MCP scope. Read tools need `raisebook:read`; write tools need `raisebook:write`.
  The scope is checked per tool with the smmist `tool_call` pattern
  (`mcp/tools/_common.py`).
- Tool handlers call the same service functions as REST. They never re-implement rules.
- Tool errors are `ToolError("<code>: <message>")` plus a JSON line with details (smmist
  `_tool_error`), using the codes in §5.2.
- Annotations: `read_only(title)` or `write(title, idempotent=…)` from `mcp/annotations.py` on
  every tool (tested). No tool is `destructive`; MCP exposes no deletes.
- Output: compact JSON objects (`mcp/shaping.py`). In lists, `notes` and bodies are cut to
  1,000 chars, and in `get_investor` to 8,000, with `"notes_truncated": true`. Null fields are
  omitted. Money is plain integers plus `currency`.

### 6.2 Reference rules (agent-friendly arguments)
- **investor** (string): a UUID, an email, a LinkedIn URL, `"Name"`, or `"Name @ Firm"`.
  Matching is exact after normalization (§3.4), not fuzzy. Zero matches → `not_found` with the
  three closest names (trigram similarity) as `details.suggestions`. More than one match →
  `ambiguous_reference` with candidates.
- **round** (string): UUID, slug, or name (case-insensitive). For tools where the round is
  *required*, omitting it uses the only open round if exactly one exists; with several open
  rounds, participant-scoped tools (`add_to_round`, `move_stage`, `set_follow_up`,
  `record_commitment`) use the investor's only open-round participation when there is
  exactly one; otherwise the tool fails with `round_required` and lists the open rounds. With
  no open round the message points to `create_round`. Where the round is *optional
  context* (`add_investor`, `import_investors_csv`, `search_investors` without round filters,
  `get_investor`, `log_activity`), omitting it means no round. `list_due_follow_ups` without a
  round covers all open rounds.
- **stage** (string): a stage key or label, case-insensitive.
- **dates**: `YYYY-MM-DD` in the workspace timezone. **timestamps**: RFC 3339; a bare date
  becomes 12:00 local time.
- **amounts**: integers ≥ 0, whole units of the round currency.

### 6.3 Server instructions (verbatim)

> Raisebook is the founder's fundraising CRM: rounds, investors, and each investor's stage in
> a round. Your API key belongs to one workspace (one company). Start with get_workspace to
> learn the rounds, valid stage keys and today's date in the workspace timezone. Refer to
> investors by id, email, LinkedIn URL, or exact name ("Name" or "Name @ Firm"). Refer to
> rounds by id, slug or name; you may omit the round when the workspace has exactly one open
> round. Amounts are whole units of the round's currency (250000 means $250k). Dates are
> YYYY-MM-DD. add_investor deduplicates by email, LinkedIn and name+firm, so call it directly
> instead of searching first. Use log_activity for what happened (email sent, call, meeting),
> set_follow_up for what should happen next, move_stage when the relationship advances, and
> record_commitment only when the investor has actually committed. Every write is recorded on
> the investor's timeline under your agent name, and the founder sees it. Never invent
> investor details; leave unknown fields empty. import_investors_csv defaults to dry_run=true:
> show the human the preview counts, then rerun with dry_run=false. Research: get_dossier
> reads an investor's cited dossier; research_investor runs research on the workspace's own
> OpenRouter key within its monthly limit; or research with your own tools and submit it with
> save_dossier (every fact cites a source you fetched; professional information only).

### 6.4 Tools

Schemas use JSON Schema types. Every tool description below is the binding tool description
text, which builders paste as the docstring.

#### 1. `get_workspace` (read)
*"Who am I and what's here: workspace name, timezone and today's date, your scopes and agent
name, every round with its stage keys, and the allowed investor types and activity kinds. Call
this first."*
Input: `{}`.
Output: `{workspace: {id, name, slug, is_sandbox, timezone, today, default_currency}, you:
{agent_name, scopes, key_prefix}, rounds: [{id, slug, name, status, currency, target_amount,
stages: [{key, label, kind}]}], investor_types: [...], loggable_activity_kinds: ["note",
"email", "call", "meeting"]}`.

#### 2. `list_rounds` (read)
*"List fundraising rounds with target, committed amount and participant counts per stage
kind. Use the slug or name as `round` in other tools."*
Input: `{status?: "open"|"closed"|"all" = "open"}`.
Output: `{rounds: [{id, slug, name, status, instrument, currency, target_amount,
committed_amount, target_close_on?, counts: {total, open, active, won, lost}}]}`.

#### 3. `get_round_summary` (read)
*"The state of a round in one call: committed vs target, soft-circled and weighted pipeline,
investors per stage, overdue and upcoming follow-ups, stale conversations (no activity for 14+
days), recent activity and warnings. Use it for status updates and 'what should I do today'."*
Input: `{round?: string}` (required; defaults to the single open round).
Output: RoundSummary (§5.3), shaped compactly (recent activity ≤ 10, top follow-ups ≤ 10).

#### 4. `search_investors` (read)
*"Find investors. `query` matches name, firm, title, email, location, tags, industries, source
and notes (all words must match). Without `round`, it searches all workspace contacts and shows
each one's stage in every round. With `round` (or any of stage/fit_min/follow_up, which imply
the single open round), it returns investors in that round with stage, fit, follow-up and
amounts."*
Input:
```json
{"query": "string?", "round": "string?", "stage": "string | string[]?", "fit_min": "integer 0-5?",
 "tags": "string[]? (all must match)", "industries": "string[]? (any matches)", "type": "investor type?",

```
Output: `{round?: {slug, name}, results: [InvestorCompact + (round ? {stage, fit, priority,

#### 5. `get_investor` (read)
*"Everything about one investor: contact fields, notes, their stage and terms in every round,
and the timeline (newest first) with who did what, including agent actions."*
Input: `{investor: string, round?: string, timeline_limit?: integer 1-100 = 20}` (`round`

Output: `{investor: Investor, participations: Participant[], timeline: Activity[],

#### 6. `add_investor` (write, idempotent)
*"Add an investor contact, or find the existing one and fill in what it is missing. Dedupes by
email, then LinkedIn profile, then name+firm, then the name alone when there is exactly one
person with that name; `matched_on` tells you which. on_duplicate: fill_empty (default: fill
empty fields, merge tags, and append new notes as a dated paragraph; it never overwrites),
return_existing (change nothing; `not_applied` lists the fields you sent that were not

Pass `round` (and optionally `stage`, `fit`, `follow_up_on`, `follow_up_note`, `next_step`,
`amount_soft`) to also put them on that round's board in the same call. Leave unknown fields
out."*

the notes and new email an agent sent for an existing investor. Name-only matching applies
when no email/LinkedIn conflicts; several same-name people give `ambiguous_reference` with
candidates. REST `POST /v1/investors` keeps `return_existing` as its default and also returns
`not_applied`.)
Input:
```json
{"name": "string (required, 1-200)", "firm": "string?", "title": "string?",
```

#### 7. `update_investor` (write, not idempotent when append_notes is used)
*"Change an investor's contact fields. Only keys in `set` change; null clears a field. Use
add_tags/remove_tags to edit tags without rewriting the list, and append_notes to add a dated

Input: `{investor: string, set?: {name?, firm?, title?, type?, email?, linkedin?, website?, x?,

Output: `{investor: Investor, changed_fields: string[]}` (an empty list means no-op and no

#### 8. `add_to_round` (write, idempotent)
*"Put an investor on a round's board, or update their round fields if they are already
there. Safe to repeat. New participants start in the first stage unless you pass `stage`.
For an existing participant, a different `stage` moves them (logged as a stage change)."*
Input: `{investor: string, round?: string, stage?: string, fit?: integer 0-5, probability?:
integer 0-100, amount_soft?: integer, next_step?: string, follow_up_on?: date, owner_email?:
string}`.
Output: `{participant: Participant, created: boolean, changed: string[]}`.

#### 9. `move_stage` (write, idempotent)
*"Move an investor to another stage in a round (for example contacted → meeting). Moving to

a commitment with an amount, use record_commitment instead of moving to the won stage."*
Input: `{investor: string, stage: string, round?: string, note?: string (≤2000)}`.
Errors: `not_in_round` (hint: add_to_round), `stage_not_found` (lists valid keys).
Output: `{participant: Participant, changed: boolean, from: Stage, to: Stage}`.

#### 10. `log_activity` (write, not idempotent unless idempotency_key)
*"Record something that happened with an investor: a note, an email (sent or received), a

dates are fine, and a future meeting time records a scheduled meeting. Pass `round` when it
concerns a specific round. Pass a stable `idempotency_key` (for example an email message id) to
make retries safe."*
Input: `{investor: string, kind: "note"|"email"|"call"|"meeting", body: string (1-20000),

Output: `{activity: Activity, duplicate: boolean}`.

*"Set or clear the date you should next follow up with an investor in a round. Give exactly

`note` says what the follow-up is for (shown in the follow-up list)."*
Input: `{investor: string, round?: string, on?: date, in_days?: integer 0-365, clear?:
boolean, note?: string (≤500)}`.
Output: `{participant: Participant, changed: boolean}`.

#### 12. `list_due_follow_ups` (read)
*"Follow-ups that are due: overdue first, then today, then (with within_days > 0) the next N
days. Without `round`, it covers all open rounds. Use it to plan the founder's outreach for
the day."*
Input: `{round?: string, within_days?: integer 0-60 = 0, include_overdue?: boolean = true,
limit?: integer 1-200 = 50}`.
Output: `{today: date, items: FollowUpItem[], counts: {overdue, today, upcoming}}`.

#### 13. `record_commitment` (write, idempotent)
*"Record that an investor committed money to a round. `amount` is the total commitment in
whole currency units (it replaces any earlier amount; it is not added to it), and 0 clears it.
By default this also moves them to the round's won stage (Committed) and adds them to the round
if needed."*
Input: `{investor: string, amount: integer ≥ 0, round?: string, committed_on?: date = today,
note?: string, move_to_won?: boolean = true}`.
Output: `{participant: Participant, previous_amount?: integer, moved_stage: boolean, round_committed_total:
integer}`.

#### 14. `import_investors_csv` (write)
*"Import investors from CSV text (first row = headers). Columns are auto-mapped from common
headers (Name, Firm/Fund/Company, Email, LinkedIn, Type, Check size, Tags, Stage, Fit,
Follow up…); pass `mapping` to override ({"Column header": "field" or null to ignore}).
Existing investors are matched like add_investor. dry_run defaults to true and returns a
preview with counts and per-row actions; show it to the human, then call again with
dry_run=false. With `round`, imported investors are added to that round, and the stage, fit,
follow-up and amount columns apply."*
Input: `{csv: string (≤2 MB), round?: string, mapping?: object, default_stage?: string,
on_duplicate?: "skip"|"fill_empty"|"update" = "skip", source?: string, dry_run?: boolean =
true}`.
Output: dry run → `ImportPreview` with `rows` cut to 50; otherwise → `ImportResult`.

#### 15. `export_round` (read)
*"Export a round's pipeline: every investor in the round with contact fields, stage, fit,
follow-up, amounts and last activity date. format=csv gives spreadsheet-ready text; json gives
structured data. Set include_activities to add each investor's timeline (json only)."*
Input: `{round?: string, format?: "json"|"csv" = "json", include_activities?: boolean =
false}`.
Output: `{round: {slug, name}, format, filename, row_count, content: string}`. Over 1 MB →
`payload_too_large` with the REST URL to use instead.

Annotation summary: read_only = 1, 2, 3, 4, 5, 12, 15. write idempotent = 6, 8, 9, 11, 13.
write not idempotent = 7, 10, 14.

### 6.6 Polish pass additions (binding)
- **Two more tools.** `create_round` (write, idempotent by name; returns the round with its
  stage keys) and `add_investors` (write; up to 50 `add_investor` items, optional shared
  `round`, one compact result line per item, a failed item does not stop the rest). 17 tools
  (22 with the research tools of §6.7).
- **Compact results.** Tools return compact JSON text (no pretty-printing, no
  `outputSchema`). Nulls and empty lists are pruned; stages are `{key, label}` (kind only in
  the funnel and `get_workspace`); UI-only fields (color, position, created_at, updated_at,
  stage_changed_at) are dropped; activities are `{id, kind, at, body?, data?, round?,
  investor?, by}` with `by` like `"claude-code · claude-opus-4-5 (agent via mcp)"`;
  `type: other` is omitted. Import dry runs list only rows that are not plain creates; commits
  return `created: [{row, id, name}]`. Import rows whose round columns are ignored because of
  `on_duplicate=skip` carry a warning.
- **Errors.** `<code>: <message>` without the SDK prefix. Argument validation reads
  `validation_error: fit must be at most 5 (got 7)`. Enum labels are accepted ("VC",
  "Family Office", "Call") and amounts may be written "250k" / "$1.5M". Messages name MCP tools,
  not REST paths. Unknown emails/LinkedIn URLs get suggestions by the same kind of key.
- **Tool list.** A key without `raisebook:write` sees only the read tools.
- **Dates.** `get_workspace` and `list_due_follow_ups` include `weekday`; `set_follow_up`,
  `add_to_round` and `add_investor` add a `warning` for a date before today;
  `list_due_follow_ups.counts` always has `next_7_days` and `next_due_on`.
- `serverInfo.version` is the Raisebook version.

## 7. Rate limits

Fixed one-minute windows in `rate_limit_counters` (Postgres, so it works across replicas),
behind `core/ratelimit.py` with `RAISEBOOK_RATE_LIMIT_BACKEND=postgres|memory|off` (tests use
`memory` or `off`, and dedicated tests cover the 429 path).

| Bucket | Limit |
|---|---|
| API key, read (GET, MCP read tools) | 600 / min |
| API key, write (POST/PATCH/PUT/DELETE, MCP write tools) | 120 / min |
| Session user, all requests | 1,200 / min |
| Imports (preview + commit), per workspace | 30 / hour |
| Exports, per workspace | 60 / hour |
| Magic-link requests | 5 / 15 min per email, 30 / hour per IP |
| Invites sent, per workspace | 50 / day |
| Unauthenticated requests, per IP | 120 / min |
| MCP protocol messages that are not tool calls (initialize, list), per key | 300 / min |
| Saving an OpenRouter key, per workspace | 10 / hour |
| Research removal requests (anonymous) | 5 / hour per IP, 3 / day per email (silently) |

A 429 carries `Retry-After`. MCP returns a tool error
`rate_limited: retry after <n>s`. `rbctl housekeeping` deletes windows older than one day.

## 8. Data rules

### 8.1 Activity rules
- Every state change writes its activity in the same transaction (one service call, one
  commit). A no-op (same stage, same date, unchanged fields) writes nothing and returns
  `changed: false`.
- Kinds and their `data`:

| kind | written by | `data` |
|---|---|---|
| `note`, `email`, `call`, `meeting` | log_activity / UI composer | `{direction?: "inbound"\|"outbound"}` |
| `stage_change` | move_stage, PATCH stage, add_to_round with a different stage, record_commitment (move), stage removal | `{from: {key,label}, to: {key,label}, reason?: "stage_removed"\|"commitment"}`; `body` = note |
| `follow_up_set` | set_follow_up, PATCH | `{from?: date, to?: date, note?}` (`to` null = cleared) |
| `commitment` | record_commitment, PATCH amount_committed | `{amount, previous_amount?, currency, committed_on}`; `body` = note |
| `investor_created` | add_investor, POST, import, sample | `{}` or `{import_run_id}` |
| `investor_updated` | update_investor, PATCH, import update | `{fields: [...], changes: {field: {from, to}}}`. Changes to `notes` record only `{"notes": {"appended": true}}` or `{"notes": {"changed": true}}`, never the text. |
| `added_to_round` | add_to_round, POST participant, import, commitment auto-add | `{stage: {key,label}}` |
| `removed_from_round` | DELETE participant | `{stage: {key,label}}` |
| `participant_updated` | add_to_round / PATCH changing fit, probability, amount_soft, owner, next_step | `{changes: {field: {from, to}}}` (owner as display label) |

- Investor `notes` edits made by a **user in the web app** do not write an activity (the
  notes field autosaves, and logging every save would flood the timeline). Notes changes by
  agents and imports do write one.
- `occurred_at` for system kinds = the injected `now`. For manual kinds it may be given: up
  to 10 years in the past and 1 year in the future.
- Deleting a manual activity is a hard delete (§4.6). System kinds cannot be deleted
  (409 `not_deletable`).

### 8.2 CSV import format
- UTF-8 (a BOM is stripped). The delimiter is auto-detected among `,` `;` and tab. RFC 4180
  quoting. At most 5,000 data rows and 5 MB. A header row is required.
- List cells (`tags`, `industries`, `stage_focus`) split on `;` or `|`, and on `,` only when
  neither of those appears.
- Dates: `YYYY-MM-DD`, `M/D/YYYY`, `D.M.YYYY`, `Oct 14 2026`, `14 Oct 2026`. Ambiguous
  `03/04/2026` is read as M/D, with a warning.
- Money: `$250k`, `250K`, `1.5M`, `250,000`, `€500k`. The currency symbol is ignored (the
  round currency is assumed), with a warning if it differs.
- Booleans are not used. Empty cells never clear existing data.

Canonical fields and the header aliases (case-, space- and punctuation-insensitive) that
auto-map to them:

| field | aliases |
|---|---|
| `name` (required) | name, full name, investor, investor name, contact, person |
| `first_name` + `last_name` | first name / last name (joined into `name` if there is no name column) |
| `firm` | firm, fund, company, organization, org, vc firm |
| `title` | title, role, position, job title |
| `type` | type, investor type, category |
| `email` | email, email address, e-mail |
| `linkedin_url` | linkedin, linkedin url, linkedin profile |
| `website_url` | website, url, site, web |
| `x_url` | x, twitter, x handle, twitter handle |
| `location` | location, city, based in, hq |
| `check_note` | check, check size, ticket, ticket size, cheque size (min and max are parsed from it) |
| `check_min` / `check_max` | min check, check min / max check, check max |
| `stage_focus` | stage focus, stages, invests at, stage |
| `industries` | industry, industries, sector, sectors, focus areas |
| `tags` | tags, labels, focus |
| `notes` | notes, note, comments, research |
| `source` | source, met at, event, list |
| `warm_intro_by` | warm intro, intro by, introducer, referred by |
| round: `stage` | pipeline stage, status, round stage (`stage` alone maps to `stage_focus` unless its values match stage keys or labels, in which case it maps to round stage) |
| round: `fit` | fit, priority, score (0-5; `hot`/`warm`/`maybe`/`low` → 5/4/3/1) |
| round: `follow_up_on` | follow up, follow-up date, next follow up, follow up on |
| round: `amount_soft` | soft, soft circle, ask, target amount |
| round: `amount_committed` | committed, commitment, amount committed, invested |
| round: `probability` | probability, likelihood, % |
| round: `next_step` | next step, next action, todo |
| round: `owner_email` | owner, owner email, assigned to (must be a member's email; otherwise a warning and the field is ignored) |

Row actions (UX pass 1, P0-6):
- `error`: only a row with no name, or one that cannot be parsed at all. The row is skipped.
- A bad **optional** cell (an unreadable date, an invalid email or URL, an out-of-range fit or
  probability, a bad amount, `check_min > check_max`) is dropped from the row with a row
  warning that names it (`follow-up left empty: "next week" is not a date`), counted in
  `warning_kinds` and `counts.cells_left_empty`, and the row still imports. Dedupe for that
  row still works by LinkedIn or name + firm. CSV, prototype JSON and the MCP
  `import_investors_csv` tool share this one service.
- With no `type` column, the type is guessed from the title or firm ("Angel" → angel,
  "… Ventures/Capital/Partners/Fund" → vc) as a row notice (`type_guessed`); otherwise it
  stays `other`, which the UI renders as "—".
- A row matching an existing investor (§3.4 order) or an earlier row in the same file: `skip`
  (default; the investor is unchanged but still added to the round if `round` is set and they
  are not in it), `fill_empty` (fills empty fields and unions tags and industries), or
  `update` (overwrites with non-empty cells and may move the stage). The action is reported as
  `update` when anything would change.
- Otherwise `create`.
- Commit runs in one transaction with one `import_runs` row. Activities are written per §8.1
  with `via=import` and `import_run_id`. Feeds show the whole run as one entry ("imported 420
  investors from investors-420.csv") through `GET /v1/activities?collapse_runs=true`; there is
  no separate summary activity.

Prototype JSON (`format: "prototype_json"`): an array of investor docs, or `{investors:
[...]}`, in the shape the prototype stores (`name, firm, title, type, industry, tags, summary,
notes, location, linkedin, website, ig, x, email, check, stageFocus, events, nextEvent,
nextEventUrl, bio, qFit, eFit, p: {<roundKey>: {stage, followUp, amount, notes, log: [{d,
t}]}}`). Mapping: `industry` → `industries[0]`; `tags` (comma string) → `tags`; `check` →
`check_note`; `stageFocus` → `stage_focus`; `linkedin` containing `/search/` → dropped (with a
warning); `summary`, `bio`, `notes`, `ig`, `events`/`nextEvent` → `notes`, as labelled
paragraphs ("Summary:", "Bio:", "Research:", "Instagram:", "Events together:"). Each
`round_map` entry maps `p[source_key]` to a Raisebook round: `stage` (prototype keys equal the
default keys; otherwise a label match; else `default_stage` with a warning), `followUp` →
`follow_up_on`, `amount` → `amount_committed` if the stage is `won`, else `amount_soft`,
`fit_field` (for example `qFit`) → `fit`, `p.notes` → one round `note` activity, `log[]` →
`note` activities with `occurred_at = d` at 12:00 local time and `data.imported_from =
"prototype"`.

### 8.3 Export formats
- **Round CSV** columns, in order: `investor_id, name, firm, title, type, email,
  linkedin_url, website_url, x_url, location, check_min, check_max, check_note, stage_focus,
  industries, tags, source, warm_intro_by, stage, stage_label, fit, priority, probability,
  amount_soft, amount_committed, committed_on, follow_up_on, follow_up_note, next_step,
  owner_email, last_activity_at, notes`. Lists are joined with `; `. The file name is
  `raisebook-<workspace-slug>-<round-slug>-<YYYYMMDD>.csv`. This CSV round-trips through
  import (the header names are canonical fields).
- **Formula-injection guard**: any cell that starts with `=`, `+`, `-`, `@`, tab or CR gets a
  `'` prefix in CSV exports.
- **Workspace JSON** (`GET /v1/export?format=json`):
  `{"format": "raisebook.export", "version": 1, "exported_at", "workspace": Workspace,
  "members": [{email, name, role}], "rounds": [Round], "investors": [Investor without rounds],
  "participants": [{round_id, investor_id, stage_key, fit, probability, amount_soft,
  amount_committed, committed_on, follow_up_on, follow_up_note, next_step, owner_email,
  stage_changed_at, created_at}], "activities": [Activity], "import_runs": [...]}`. API keys,
  sessions and tokens are never exported.
- **Round JSON**: `{"format": "raisebook.round", "version": 1, "round": Round,
  "participants": [Participant + investor fields + (include_activities ? timeline : [])]}`.

### 8.4 Privacy and deletion semantics (binding product promise)
The promise, word for word (landing and `/privacy` use this text):
1. **Your data is yours.** A workspace is visible only to its members and to the API keys
   its owners create.
2. **We never pool, sell, rent or mine it.** Raisebook never builds an investor database from
   your data and never shows one workspace's data to another.
3. **No ads, no trackers.** No analytics scripts, pixels or third-party cookies. Fonts are
   served by Raisebook.
4. **No AI on your data unless you bring it.** Raisebook never runs or pays for AI on its
   own. Investor research runs only when you press a button, on your own OpenRouter key, and
   sends only the investor's name, firm and links, your company profile and round terms.
   Agents you connect use your key, and every action they take is on the timeline.
5. **Leave any time.** Export everything as CSV and JSON. Delete your workspace or account
   permanently, effective immediately.
6. **Check our work.** Raisebook is open source under AGPL-3.0, including the code that
   handles your data.

Semantics:
- **Isolation**: every query on a workspace-scoped table filters by the caller's
  `workspace_id`. Services take a `WorkspaceContext` (from the principal), never a raw id
  from input. Composite FKs block cross-workspace links (§3).
- **Delete investor / round / workspace / account** are hard deletes in one transaction (no
  soft-delete columns, no tombstones). Workspace delete cascades everything, including API
  keys, invites and import runs. Account delete is described in §5.4.
- **Backups** (when hosted) are retained for at most 14 days. Deleted data leaves backups
  when they expire. The privacy page says this.
- **Logs** contain request id, method, route template, status, duration, workspace id, actor
  type and key prefix. They never contain request bodies, query strings, investor fields,
  emails (an email is hashed when a log line needs it) or tokens.
- **Email** (magic links, invites) goes through the configured SMTP provider. Only the
  recipient address and the message leave the system.
- Sandbox workspaces work exactly like real ones, and can also be deleted.
- **Research** (docs/RESEARCH-SPEC.md) is private to the workspace. Public facts
  (`research_sources`, `investor_identities`, `dossier_facts`) are stored apart from private
  analysis (`dossiers`, runs, suggestions). Only professional information is kept; phones and
  addresses are stripped and private topics dropped, for model and agent dossiers alike.
  Anyone can ask (Research Policy) for what research stored about them to be deleted in every
  workspace; research about them is then refused. Founders' own contact rows stay.
- The OpenRouter key is sealed with a server key (envelope encryption), never returned (last
  4 characters only), redacted from logs, and deleted at once on "Remove key".

## 9. Quality bar and testing

### 9.1 Backend
- `uv run pytest -q`, `uv run ruff check . && uv run ruff format --check .` and
  `uv run mypy raisebook` must be clean. mypy is strict on `raisebook.auth.*`,
  `raisebook.services.normalize` and `raisebook.services.csv_io`.
- The test harness copies smmist: real Postgres at `RAISEBOOK_TEST_DATABASE_URL` (default
  `postgresql://localhost/raisebook_test`), one schema per pytest session
  (`t_<pid>_<hex>`), `alembic upgrade head` into it, an outer transaction per test rolled
  back, and httpx ASGI clients. No network calls (email uses an in-memory outbox fixture).
- An injectable clock everywhere (`core/clock.get_now`, MCP `Clock`). Tests freeze it.

### 9.2 Mandatory test suites
1. **Auth**: magic-link request, verify, single use, expiry, rate limit; session cookie
   tamper; CSRF required on unsafe methods; signout; API key create, use, revoke, expire,
   wrong-mode prefix.
2. **Permissions**: the §4.6 matrix as a parametrized test, for each role and each key scope.
3. **Workspace isolation** (`tests/isolation/`): two workspaces A and B with data. For
   **every** `/v1` route (enumerated from `app.routes`, so a new route without coverage fails
   the test) and **every** MCP tool, a principal of A addressing B's ids, slugs or references
   gets 404 / `not_found`, and B's data is unchanged. List endpoints never return B's rows.
   Search with B's investor names returns nothing for A.
4. **API**: each endpoint's happy path plus its main errors.
5. **MCP**: via the real `/mcp` route (JSON-RPC over the ASGI client): tool list and
   annotations, every tool's happy path, reference resolution (ambiguous, not found,
   round_required), idempotency (add_investor twice, add_to_round twice, move_stage to the same
   stage, log_activity with a key twice, record_commitment repeated), agent attribution
   (`X-Agent-Name`/`X-Agent-Model` reach activities).
6. **Import/export**: auto-mapping, every dedupe path, within-file duplicates, error rows,
   dry run writes nothing, round columns, prototype JSON, the CSV round-trip
   (export → import into an empty workspace → same data), the formula guard.
7. **Deletion**: investor, round, workspace and account cascades; the append-only trigger
   (UPDATE fails; FK SET NULL succeeds).

### 9.3 Web
`npm run lint && npm run typecheck && npm run build` clean. Every screen is checked at 360px
and in dark mode. No third-party requests at runtime.
